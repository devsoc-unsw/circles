# degree-eval decisions

Rulings made while implementing SCHEMA.md (revision 3) where the spec is silent or ambiguous.
EVALUATOR.md §6 asks for these to be recorded. Each one should be confirmed or overturned in the spec.

## Conformance (§15)

All 10 fixtures pass as written, on their first execution. No fixture or spec text had to change.

## Evaluation

1. **Component order.** A double degree's component groups come before the program's own
   `requirements` in pre-order (§8 gives no order). Pre-order matters for core matching and pool order.
2. **Repair order (§7.4 step 7).** Unmet core items are repaired first (canonical item order), then
   pools (canonical pool order). The spec says "core item or pool … in canonical order" without
   saying how the two orders interleave.
3. **Inactive and display-only nodes.** A `limit` with an inactive scope, and an `info` node with
   `confirm: false`, report `status: met` with `inactive: true`; parents ignore them.
4. **Exemption UOC reduction (§7.2 step 5).** "The enclosing node's declared `uoc`" is read as the
   nearest ancestor with a declared `uoc` (e.g. a component), plus the program total.
5. **Static contexts (§5.3).** `pending` results do not count as done: "completed instances only".
6. **`complete(path)`** re-runs allocation on the instances done before τ, two levels deep at
   most. A `complete()` inside that re-run reads `unknown`.
7. **Auto-choice (§7.5).** Subsets are generated by size range and sorted as index lists. Ties
   keep the earliest subset.
8. **Subtree uoc check.** A selected spec's `uoc` check (the spec node's `uoc` override, else the
   spec document's) is evaluated on its `slot/CODE` subtree. The spec node takes the reasons of the
   subtree that decided its status.
9. **Structural reasons.** A group, spec or root carries the reasons of the children that decided
   its status (unmet ones, else unknown ones), so a reason like `overlap_undeclared` is visible at
   the spec node, as the fixtures expect.

## Loading and validation

10. **Lenient schema (§10).** For a newer minor version, every structural error is a warning, not
    only unknown fields. Fail-safe evaluation (`unknown`, never a wrong `met`) is the evaluator's job.
11. **`uri` format.** The browser validator only checks for a scheme and no spaces (looser than
    ajv-formats' full URI rule). `tools/validate.mjs` remains the strict authoring check.
12. **`extends` documents** are parse-checked on their own requirements only. Ancestors are checked
    as documents in their own right.

## Performance (EVALUATOR.md §5.6, measured for M7)

`npm run bench`, 2026-10-11, Node 26 on the development laptop (Apple Silicon), median of 50 runs:

| case | median | p95 | budget |
|---|---|---|---|
| 3778 + COMPA1 + MATHC2, 144 UOC: load and validate the documents | 1.5 ms | 1.8 ms | — |
| 3778 + COMPA1 + MATHC2, 144 UOC: evaluate | 0.5 ms | 2.0 ms | 50 ms |
| 3409 golden plan, 144 UOC: evaluate with selections | 2.1 ms | 2.6 ms | 50 ms |
| 3409 golden plan: evaluate with both choice groups auto-chosen | 3.1 ms | 4.1 ms | 300 ms |

Spec slots are never enumerated by auto-choice (§7.5), so an unselected 3778 is not a slow case;
3409's `choose` groups are the realistic auto-choice load.
